## 从这里开始：先体验，再看它为什么成立

你可能已经让 AI 做过一个页面。它很快给出一张完整界面：大标题、渐变背景、几张卡片、一个发光按钮。第一眼似乎不错，换成真实内容以后，问题才出现：标题变长就挤坏布局，手机菜单打不开，按钮有动效却没有明确状态，改一处又影响另一处。

问题未必是 AI 不会写代码。也可能是我们给了它一个愿望，却没有给它足够明确的任务、可用材料和判断标准。

**这个专题要帮助你完成的，不是生成一张漂亮截图，而是交付一个能被理解、能被操作、能被继续维护的界面。**

我们把这件事拆成一条可以重复使用的路径：

**明确任务 → 提取参考规则 → 选择资源 → 描述交互 → 组合与实现 → 验证 → 沉淀与更新。**

你不必先成为前端专家，但需要学会判断：哪些决定值得交给 Agent，哪些信息不能省，什么结果才算完成。

### 本专题的两个约定

**用我们讲述的方法，建设我们自己的产品。** 我们会以 Vibes 的 Topic 页面改造为贯穿案例，公开选了什么、为什么选、改了什么，以及哪里还没有验证。自用能够提供案例，不能自动证明某种方案对所有人最好。

**让知识同时适合人和 Agent。** 人可以体验组件、阅读解释；Agent可以按需读取用途、行为、接口、来源与验证材料。视觉效果不会被几句文字完全替代，但没必要每次找组件都从头观察几十个网站。

## 01 AI 改变了 UI 开发的什么

**变化不是“从此不用设计”，而是设计意图与运行结果之间的衔接方式发生了变化。**

### 三种工作方式，不是三个互相取代的职业

下面是为了理解而简化的工作流模型，不是所有团队都遵循过的统一历史。

| 环节     | 人工衔接为主             | 只把 AI 当代码生成器 | 本专题倡导的 AI 原生流程             |
| -------- | ------------------------ | -------------------- | ------------------------------------ |
| 明确任务 | 人整理需求与用户路径     | 输入“做一个高级页面” | 人确定目标，Agent补齐状态与约束      |
| 形成方向 | 人找参考、画原型、写规范 | 让模型凭默认偏好生成 | 参考、真实内容、设计规则共同约束结果 |
| 选择材料 | 人查文档、试组件         | 模型凭记忆生成或安装 | 检索真实来源，核对版本与项目适配     |
| 实现     | 人完成布局与接线         | 不断说“再好看一点”   | 分轮实现，每轮有明确输入和退出条件   |
| 验证     | 人工体验与自动测试配合   | 页面能打开就认为完成 | 检查任务、状态、视觉、边界和资源成本 |
| 沉淀     | 维护设计系统和组件       | 留下难解释的一批代码 | 记录配方、理由、实际证据与失败边界   |

AI 不会消除“我要交付什么”这个问题。它更可能放大输入的质量：约束清楚时，能更快推进；约束模糊时，也能更快生成一大堆不一致的东西。

现有工具已经在连接这些环节。Figma MCP 可以向 Agent 提供设计变量、组件和布局信息；shadcn 的 registry 描述组件文件与依赖，MCP 提供组件检索和取用入口。它们说明设计上下文与代码资源能够被直接传递，但不保证任何一次生成都符合产品目标。[Figma 官方说明][figma-mcp] · [Registry 结构][shadcn-registry] · [shadcn MCP][shadcn-mcp]

### 用 AI 开发 UI，与为 AI 产品设计 UI，是两件事

**用 AI 开发 UI** ：让 Agent帮助你理解项目、找资源、写布局、调试和验证。一个普通报表页也可以这样开发。

**为 AI 产品设计 UI** ：让界面表达不确定等待、流式结果、工具调用、审批、取消和失败恢复。即使代码完全由人编写，也要解决这些问题。

我们同时讨论两者，但不会把“加一个思考球”当成 AI 原生设计的证明。

### 人应该保留什么判断

人需要决定用户的目标、重要程度、风格方向、可接受代价和执行授权。Agent可以帮忙分析和提出选择，但不能替用户决定把什么数据交给外部服务，也不能用自动生成的截图替代真实使用判断。

遇到不满意的结果，先检查输入，而不是马上换模型：任务是否具体？参考是否说明了借鉴点？现有框架是否被读取？真实内容是否已经放进去？“完成”有没有可检查的定义？

**本章带走：** 一张开发地图。接下来每一章都为下一步提供材料；发现新约束时可以返回前一环，不必假装开发是一条不能回头的直线。

## 02 开始之前，先定义你要交付的界面

**在收藏第十个灵感网站之前，先写清楚一个用户要在什么场景下完成什么事。**

“做一个 UI 资源网站”太宽。“帮助正在改造已有网站的人，找到合适的交互组件，并带走可执行的接入方案”，才开始接近可设计的任务。

### 贯穿案例：把 Vibes 的组件演示页改造成可使用的 Topic

原页以十种 beUI 演示为主，每节有操作方式、预期反馈和来源。它已经提供了可体验的材料；本次设计目标是在这些材料之上，增加方法主线、资源选择、交互说明和取用路径，而不是把组件数量继续翻倍。[原页源码][vibes-original]

下面是这次改造的任务说明。它是设计目标，不是已经完成的产品报告。

| 字段       | Vibes 案例                                                          |
| ---------- | ------------------------------------------------------------------- |
| 使用者     | 希望借助 AI 开发或改造 Web 界面的独立开发者                         |
| 使用场景   | 一边理解方法，一边为自己的项目寻找材料；可能在手机上阅读            |
| 主要任务   | 理解一个交互，找到适合的实现，带走接入与验收材料                    |
| 主要内容   | 方法、资源、真实演示、交互规格、配方、来源与验证记录                |
| 第一版交付 | 完整专题正文、复用演示、分类目录、可复制任务包                      |
| 后续交付   | 筛选工作台、方案清单、查看做法模式和结构化贡献入口                  |
| 保留约束   | 不为了本专题更换现有框架，不破坏普通阅读，不偷偷扩大本地 Agent 权限 |
| 不做       | 本轮不建立任意代码在线执行服务，不让公众 MDX 未经审查直接进入生产   |
| 成功标准   | 读者能找到一个合适方案并解释选择理由；接入结果与验证状态可以追溯    |

### 先设计状态，不要只设计一张“成功画面”

资源目录至少会遇到：有结果、无结果、来源失效、兼容性未知、资料正在核对、已选中、已取消。执行任务又会遇到：未开始、等待确认、进行中、失败、取消请求已发出、结果仍未知。

这些状态不一定都需要复杂组件，但不能等写完页面才发现没有地方放。

一个很实用的检查方式是把正式文案提前放进去：长中文标题、超长网址、缺失字段、两条互相冲突的限制。只有理想英文短句的设计，不能证明它适合真实内容。

### 从小白描述到可执行要求

不必先背专业名词。你可以先说：“点开助手以后，正文不要突然换行，回来时还在原来阅读的位置。”再让 Agent解释它准备怎样保留布局和滚动，并用实际页面验证。

反过来，听上去专业的词也不等于要求清楚。“使用现代设计系统，增强体验”依然无法验收。

## 03 寻找灵感，把好看变成可执行的设计规则

**收藏截图只是储存偏好，拆解截图才是在形成设计输入。**

### 参考时看关系，不要只看装饰

对每个参考，尝试回答四个问题：第一眼看到了什么？主要动作在哪里？相关信息怎样靠近，无关信息怎样分开？动效到底解释了什么变化？

还要写出“不采用什么”。例如：借鉴导航的信息层级，不采用持续滚动背景；借鉴卡片内部的排版，不复制品牌素材；借鉴结果对比方式，不照搬整张营销页面。

对 Vibes 这样的长篇知识页面，我们更关心读者能否定位问题、连续阅读、查看证据与返回原位置，而不是每次滚动都出现新的惊喜。

### 把模糊形容词改成观察与约束

| 原来的要求 | 更容易落地的表达                                             |
| ---------- | ------------------------------------------------------------ |
| 高级一点   | 降低同时争夺注意力的元素数量，建立明确的主次层级             |
| 留白舒服   | 说明同组元素、区块之间、章节之间的距离关系，并用真实内容核对 |
| 动画丝滑   | 指明哪个状态触发、哪些元素变化、能否中断、减少动态效果时怎样 |
| 有科技感   | 先定义需要表达的信息，再决定是否采用特殊材质或动效           |
| 像这个网站 | 列出借鉴的具体特征，以及不复制的品牌、内容和业务结构         |

这些表达仍然需要视觉判断。它们的作用是让讨论有对象，而不是把审美压成一条万能规则。

## 04 选择资源：从基础组件到完整界面

**资源越多，越需要知道自己正在选哪一种东西。**

### 两个维度，不要混成一棵树

按开发用途，你需要灵感、设计规范、组件、模板、工具和验证资料。按组合尺度，界面可以从参数、基础行为，一直组织到整页流程。

下面是 Vibes 为检索和教学提出的工作分类，不宣称每个库都使用同样的术语。

| 尺度            | 含义                   | 例子                                 |
| --------------- | ---------------------- | ------------------------------------ |
| Design tokens   | 跨组件共享的设计参数   | 字体、颜色、间距、圆角、动效时长     |
| UI primitives   | 基础交互与组合能力     | 弹层、焦点管理、页签行为、滑杆机制   |
| Components      | 可直接使用的具体控件   | 按钮、输入框、卡片、状态标签         |
| Blocks          | 完成局部任务的组件组合 | 上传区、搜索与筛选、方案比较区       |
| Screens / flows | 完整页面和跨页面流程   | 资源工作台、注册流程、生成与编辑流程 |

“内容组件”是另一个用途维度：时间线、图表、Before/After 和可玩演示服务于知识表达。它们不必硬塞在所有 UI primitives 与 blocks 之间；一个内容组件内部也可能组合多种基础控件。

### A. 先选基础，再选特色

| 资源                      | 官方提供的主要能力                   | 本专题建议的选用时机                 |
| ------------------------- | ------------------------------------ | ------------------------------------ |
| [Radix Primitives][radix] | 可定制、注重可访问性的低层 UI 组件   | 需要自己控制样式，同时复用基础交互   |
| [Base UI][baseui]         | 无预设视觉样式的 React 组件          | 希望把交互能力接进已有视觉体系       |
| [React Aria][reactaria]   | 注重可访问性与多种交互方式的组件能力 | 需要认真处理键盘、触摸与复杂控件     |
| [shadcn/ui][shadcn]       | 可取用、修改和组合的组件源码         | 想从现成组件基础开始，并在项目内维护 |
| [Motion][motion]          | React 动画及动效偏好处理能力         | 已经需要复杂交互动画，再评估引入     |

这些是候选，不是让你五套全装。已有项目优先复用已经在使用、能够满足要求的基础；选另一个库时，说明缺口与代价。[Radix 说明][radix] · [Base UI 说明][baseui] · [React Aria][reactaria] · [shadcn 介绍][shadcn]

### B. 用特色组件补充表达，不让特色重新定义整站

| 资源                       | 可取用的方向                                                        | 接入前重点检查                                     |
| -------------------------- | ------------------------------------------------------------------- | -------------------------------------------------- |
| [Great UI][greatui]        | React 与 Tailwind 组件及特色效果                                    | 实际组件源码、依赖、样式影响和具体许可             |
| [MicroKit][microkit]       | React / CSS 微交互，按组件复制；官网提供 JS/TS 与 CSS/Tailwind 选择 | 具体条目需要什么依赖，不假设每项零依赖             |
| [Rare UI][rareui]          | 动画 React 组件，官网提供 shadcn CLI 取用入口                       | 对应条目的安装指向、版本和需要修改的文件           |
| [Animata][animata]         | 可复制的动画 React 组件                                             | 官网的可访问性等声明与具体实现验证分开记录         |
| [Libraries.dev][libraries] | 包括 Thinking orbs 的 AI 界面组件与 Copy prompt 入口                | 状态映射必须对应真实业务，不因动效而编造“思考过程” |
| [beUI Motion][beui]        | 本页已有的按钮、页签、选择、状态和布局演示                          | 保留来源与许可，区分原版样本和产品化改造           |

本轮已阅读这些项目的官方页面以核对主要定位和取用方向； **除现有 beUI 接入外，没有在本次初稿工作中把上述库逐个安装进 Vibes。** 即便某个库已有成功案例，也不意味着其所有组件都适配你的项目。

组件数量、免费额度和具体安装语法会变化。本专题不把“多少个组件”当成永久结论；真正使用时应打开当前条目、锁定版本、记录得到的源码与依赖。

### C. 设计工具、SaaS 与 Agent 接口不是组件库

| 资源                             | 用来完成什么环节                        | 带回当前项目什么                                   |
| -------------------------------- | --------------------------------------- | -------------------------------------------------- |
| [Figma MCP][figma-mcp]           | 在设计上下文与 Agent 工作流之间传递信息 | 设计变量、组件、布局与必要资源                     |
| [v0][v0]                         | 从要求与参考形成可运行界面方向          | 经检查的原型与代码，而不是默认替换现有架构         |
| [Framer][framer]                 | 可视化站点设计、内容组织与发布          | 设计与站点方案；项目可迁移性、账号与发布条件需另查 |
| [shadcn MCP][shadcn-mcp]         | 查找和取用 registry 资源                | 实际组件、依赖与接入材料                           |
| [Storybook Manifests][storybook] | 为 Agent 提供组件接口与使用材料         | 项目真实组件的结构化上下文                         |

平台能生成或发布页面，不等于它的产物能无成本迁移到任何仓库。上传设计文件、客户资料或私有代码前，先核对数据流向、使用条件与授权。这里不提供未核对的价格或免费额度。

### D. 当内容不只是文字，应该选什么表达方式

| 要解释的问题         | 内容组件              | 不可省略的内容                                               |
| -------------------- | --------------------- | ------------------------------------------------------------ |
| 一个流程怎样推进     | Workflow demo         | 输入、输出、节点关系；真实执行与演示回放分开                 |
| 哪种方案适合我       | Interactive benchmark | 数据来源、版本、条件、指标定义；权重变化不能伪装成客观总排名 |
| 改造前后差在哪里     | Before/After          | 同一对象、可比条件、差异说明                                 |
| AI 视频如何生成      | Video showcase        | 输入、素材来源、模型或工作流版本、人工修改记录               |
| 一段代码怎样工作     | Runnable code         | 环境与执行边界；不能让任意代码直接取得主站权限               |
| 连续参数如何改变结果 | Slider comparison     | 参数含义、取值；预生成样本必须标为回放，不冒充实时推理       |
| 一个产品如何演进     | Timeline              | 事件日期、来源、版本关系；更新日期不替代事件日期             |
| 数据支持什么结论     | Chart                 | 单位、数据表、来源、样本范围和限制                           |
| 作品实际能做什么     | Playable demo         | 启动、退出、重置、来源与运行隔离                             |

这些是表达模式，不是本页都已实现的九个新功能。选择原则很简单： **交互必须让某个关系更容易被观察，而不是让页面看上去更忙。**

### 一份资源选择清单，胜过十个同时安装的库

以 Vibes 的 Topic 改造为例，首版可以先复用已有 MDX、正文样式和 beUI 演示，用原生折叠与表格承载额外信息。只有资源筛选、参数联动或任务包生成出现真实需求时，再实现对应的内容区块。

| 候选                  | 为什么需要               | 能否复用现有能力   | 新增代价               | 结论             |
| --------------------- | ------------------------ | ------------------ | ---------------------- | ---------------- |
| 已有 Tabs / Accordion | 展示不同视图或补充说明   | 先检查现有实现     | 主要是内容与交互适配   | 优先复用         |
| 新动效库              | 某个效果现有能力无法表达 | 必须先证明缺口     | 依赖、样式与测试成本   | 有明确收益再引入 |
| 完整网站模板          | 从零建立站点结构         | 本案例不是从零建站 | 可能覆盖当前框架和样式 | 不作为默认方案   |
| 新资源筛选区块        | 目录规模使手动查找困难   | 静态目录先验证分类 | 状态管理、搜索和验收   | 后续单独设计     |

**本章带走：** 资源组合与选择理由。下一章把“选中了什么”进一步变成“它应该怎样工作”。

## 05 把交互翻译成 Agent 能理解的说明

**不要只告诉 Agent“效果很丝滑”。要告诉它谁触发了什么变化，变化怎样结束，遇到异常怎么办。**

### 从外观描述，走向行为约定

回到开场的 Tabs。一个模糊要求是：“做一个有滑动动画的胶囊页签。”一个更有效的规格，会说明页签切换哪些内容、选中和焦点是否同步、能否连续切换、长标签如何处理，以及不需要动效时怎样保留状态。

下面是准备实现一个页签区块时应填写的说明，不是对原 beUI 源码的逐项测量报告。

| 维度       | 要写清楚的问题                                     |
| ---------- | -------------------------------------------------- |
| 用途       | 为什么使用页签，而不是同时显示内容或使用折叠？     |
| 输入与触发 | 点击、触摸和键盘分别怎样进入与切换？               |
| 状态       | 当前选中项、当前焦点、禁用项、内容就绪状态是什么？ |
| 可见变化   | 指示器、文案和内容区域分别怎样变化？               |
| 时间与中断 | 参数来自源码还是建议？连续选择时怎样转向新目标？   |
| 降级       | 关闭动画以后，当前项是否仍然清楚？                 |
| 边界       | 长标签、窄屏、内容缺失、加载失败怎样处理？         |
| 接入       | 源码、依赖、真实参数和目标项目条件是什么？         |
| 证据       | 哪些已核对，哪些只观察过，哪些还未知？             |

键盘行为不应该凭模型习惯随意发明。以页签为例，W3C APG 区分自动激活和手动激活，给出角色、关联关系及键盘操作建议；应根据内容加载条件选择策略，并验证具体实现。[Tabs Pattern][apg-tabs]

### 实验：外观相近，不代表语义相同

开关、复选框和单选组都能改变一个小标记，但它们表达的用户意图不同。我们建议先根据选择关系确定控件，再选择外观。

| 选择关系               | 通常应考虑   | 需要说明的行为                       |
| ---------------------- | ------------ | ------------------------------------ |
| 开启或关闭某个设置     | Switch       | 是否立即生效，保存失败后怎样恢复     |
| 多项可以分别选中       | Checkbox     | 选择是否独立，是否需要提交或批量操作 |
| 一组互斥的方案         | Radio group  | 同一时间只能有一个选中，默认值是什么 |
| 有顺序的连续或离散数值 | Range slider | 范围、单位、步长以及键盘替代路径     |

折叠适合补充说明和实现细节，不适合隐藏关键风险、费用条件或主要动作。用户应在决定使用之前看到会影响决定的信息。

### 为 AI 产品表达状态：不能让动效替后台编故事

<BadgeDemo client:visible />

上面的 Syncing、Synced、Review、Failed 是原演示自动轮换的状态样本， **没有连接真实任务** 。它展示怎样表达变化，不证明一个 Agent 正在同步或已经成功。[原组件][beui-badge] · [演示说明][vibes-original]

如果把类似组件用于真实任务，本专题建议至少区分这些情况：

| 实际条件               | 可以表达什么                 | 不应该表达什么                 |
| ---------------------- | ---------------------------- | ------------------------------ |
| 请求已经发出，细节未知 | 正在处理，具体阶段未知       | 编造“检索、推理、验证”逐步完成 |
| 后台明确等待用户授权   | 等待确认，并提供操作入口     | 一直显示加载，把责任留给用户猜 |
| 用户发出取消请求       | 正在请求取消                 | 未确认就声称远端任务已完全停止 |
| 部分结果已经返回       | 明确标注可用的部分           | 把部分结果标为完整成功         |
| 网络中断，执行结果未知 | 连接中断，结果待确认         | 自动重发可能产生副作用的操作   |
| 后台明确返回失败       | 失败原因、可重试或修正的路径 | 用一个红色图标替代原因和下一步 |

这是一份推荐的设计约定，不是某个通用 Agent 协议。具体字段必须与实际后端对齐。

### 翻译库要保存模式、实现和实践，不只保存组件名称

**模式** 描述通用问题，例如“移动选中指示器”。 **实现** 描述某个项目怎样提供这种行为，包括源码、版本和参数。 **实践** 记录一个真实产品采用哪种实现、做了哪些修改、验证到什么程度。

同一模式可以有多个实现，同一实现可以有不同环境下的实践记录。这样，一个库停止维护，不会让整个模式知识随之失效。

### 怎样提取：源码优先，运行核对，视觉补充

有源码时先读接口、事件、状态、CSS 或动画代码；有正式设计文件时读取变量与组件关系；只有网站效果时，就记录能观察到的内容，不猜内部实现。MDN 的 `getAnimations()` 可用于取得影响元素的 CSS 动画、过渡和 Web Animations，但不能据此声称能完整解析任意 Canvas、WebGL 或自定义渲染。[API 说明][mdn-animations]

原链接、实际演示和关键视觉证据仍应保留。文字负责降低检索和理解成本，不负责替代最终的视觉判断。

### 按需披露，而不是一次塞给 Agent 全部资料

| 阶段 | 提供什么                               | 用来做什么         |
| ---- | -------------------------------------- | ------------------ |
| 发现 | 用途、效果摘要、技术栈、重要限制与状态 | 找到少量候选       |
| 比较 | 行为、适用场景、依赖和替代方案         | 解释为什么选择     |
| 执行 | 固定来源、真实接口、配置与验收步骤     | 接入项目           |
| 核对 | 原演示、源码、验证和失败记录           | 检查效果与解决争议 |

现有 shadcn Registry、Storybook Manifests 和 Agent Skills 分别提供资源描述、组件上下文和按需加载组织方式。可以沿用这些能力，不必重新发明每个接口；Vibes 更需要补齐跨资源的行为解释、选择理由和真实实践证据。[Registry][shadcn-registry] · [Manifests][storybook] · [Agent Skills][skills]

**本章带走：** 一份能区分观察、要求和验证结果的交互规格。它比“做得更高级”更容易实现，也更容易检查。

## 06 让 Agent 组合、实现，并把界面打磨到位

**现在交给 Agent 的，应是一组相互关联的材料，而不只是一张截图。**

### 四轮实现，每轮只解决一类主要问题

| 轮次 | 主要任务                             | 这一轮结束时应能看到什么             |
| ---- | ------------------------------------ | ------------------------------------ |
| 结构 | 真实内容、主要任务路径、布局与分组   | 不靠动效也能理解和定位内容           |
| 功能 | 选择、切换、状态、错误和必要数据接线 | 主要操作真实工作，演示与业务明确分开 |
| 统一 | 字体、颜色、间距、尺寸、响应式和主题 | 不同来源的组件属于同一个产品         |
| 打磨 | 动效、焦点、滚动、中断和极端内容     | 细节服务于任务，不破坏其他路径       |

每一轮保留可运行的版本和明确差异。不要一边让 Agent 换框架，一边改视觉，一边再加十个功能；否则结果变差时，很难知道是哪种改变造成的。

### 一个完整的示范决策链

我们用“资源条目的演示与实现说明”作为局部案例。下面是实施设计，不是已经发布的新工作台。

**任务：** 读者在不离开当前 Topic 的情况下，理解一个组件、确认适用条件并带走接入材料。

**内容：** 用途、演示、框架与依赖、来源、验证状态、限制、接入步骤。

**结构选择：** 短的用途与重要限制始终显示；较长的源码说明可折叠；需要直接对照的数据同时显示，而不是藏在不同页签。

**材料选择：** 优先检查现有 beUI 和正文组件。没有必要因为一个资源卡就引入整套新网站模板。

**交互约定：** 查看源码不是安装；加入执行清单不是运行；复制失败时提供可选取文本。若后续增加“交给 Agent”，默认形成可检查的草稿，而不是静默执行。

**验收：** 鼠标、触屏和键盘可以完成主要动作；长中文标题不遮挡控制；没有 JavaScript 时说明与来源仍可读；执行状态不能由演示动画伪造。

这个链条说明了为什么先写任务与规则。最终选择 Tabs 还是 Accordion，来自内容关系，而不是先找到一个组件再为它发明需求。

### 为什么几个好看的组件拼在一起，仍然不好看

不同组件可能采用不同字体、圆角、阴影、间距和反馈方式。它们在各自官网里协调，放到同一产品里却可能互相争夺注意力。

解决办法不是每个组件单独“调到好看”，而是先决定共享规则，再做局部适配。保留需要的行为，把颜色、字体、图标、间距和状态文案接到产品自己的规则上。

**原版演示和产品使用要分开维护。** 原版演示帮助核对来源；产品化版本服务当前任务。改过的效果就说明改过，不把 Vibes 的适配当成上游原样能力。

### 实验：按钮很特别，但它必须清楚地告诉你会发生什么

<ButtonDemo client:visible />

这是 beUI 的 Metallic Button 演示，Continue 和 Generate 不执行继续、生成或购买。观察反馈以后，再问：实际项目里按钮应该叫什么？处理期间能否重复点击？失败时从哪里继续？[原组件][beui-button]

一个有金属光泽的按钮仍然需要清楚的名称和状态。对于危险操作、付费调用或权限授权，外观不能替代说明。

### 间距不是一串数字，而是一组关系

可以按以下顺序检查页面：先看主要信息层级，再看组内与组间关系，接着看对齐与宽度，最后看局部数值。不要遇到拥挤就只增加高度，也不要为了“信息密度”把所有文字压到一起。

同一张卡片应至少放入短标题、两行中文标题、缺失说明、长网址和多个状态标签。检查它们后，再确定高度策略、文本换行和必要的展开方式。

**与其要求“间距完美”，不如要求“相同层级遵循一致规则，真实内容不会破坏阅读关系”。**

### 丝滑不仅是动画，更是没有意外

本专题把“丝滑”拆成四个可讨论的目标：操作反馈及时，状态变化连续，布局不无故跳动，重复操作与中断有明确结果。漂亮的缓动曲线解决不了所有问题。

先让正确状态可以被看见，再决定是否需要过渡。减少动态效果时，保留信息而减少非必要运动。Motion 提供相关处理能力，W3C 也给出交互动效可关闭的指导；具体组件仍需自己实现和核对。[Motion 可访问性][motion] · [W3C 动效说明][wcag-motion]

### 实验：哪些内容不应该不停移动

<MarqueeDemo client:visible />

这里的品牌名称来自 beUI 的演示素材，不代表它们使用或支持 Vibes。原示例支持悬停暂停，并为减少动态效果保留静态显示。[原组件][beui-marquee] · [现有演示说明][vibes-original]

我们可以用 Marquee 展示不要求逐项阅读的装饰样本，但不建议把资源限制、重要来源或必须比较的数据放进持续移动区域。这个演示的价值，也包括帮助我们决定何时不用它。

### 放进 MDX，并不意味着所有内容都交给 React

MDX 可以导入组件。在 Astro 中，浏览器交互需要相应的客户端指令；本页沿用 `client:visible`，将组件启动与进入可视区关联。正文、来源和说明仍应保持静态可读。[Astro MDX][astro-mdx] · [项目现有规则][vibes-mdx]

按需加载不会消除资源成本。初次进入页面、滚过多个演示、收起后再打开，都值得检查。进入可视区后加载过的组件，也不会因为名字叫“懒加载”就保证离屏后自动停止所有工作。

对于以后加入的 Runnable code 或 Playable demo，应单独设计执行、网络和存储边界；不能把任意第三方代码直接放进有主站权限的 React 组件。MDX 是可执行源码，不是未经审查公众内容的安全容器。

## 07 从看起来完成，到可以交付

**截图证明某个时刻看起来怎样，不能证明整个任务流程已经正确。**

### 先列出会让用户失败的问题

验收不等于把能想到的所有测试都堆上去。先看主要任务有没有被阻断，再看错误和边界，最后打磨不影响任务的细节。涉及数据、权限、误操作和错误状态的问题，不能被“只是个 UI”轻轻带过。

| 检查组     | 核心问题                                             | 可记录的证据                       |
| ---------- | ---------------------------------------------------- | ---------------------------------- |
| 任务与状态 | 能否完成主要动作？无结果、失败、重复操作和中断怎样？ | 操作步骤、实际结果、事件或状态记录 |
| 阅读与操作 | 中文长文本、手机、键盘和减少动态效果怎样？           | 指定环境下的实际操作与截图         |
| 边界与来源 | 有没有未授权操作、秘密暴露或未经审查的代码？         | 来源、修改清单、权限与数据流说明   |
| 性能与维护 | 加载、连续使用、退出后是否有明显退化？               | 构建资源、运行观察和定位结果       |

### 视觉检查与功能检查互相补充

视觉对比适合发现布局、字体、颜色或组件位置的意外变化，但不替代交互测试。比较时应控制浏览器、视口、字体、数据和动画状态；Playwright 的官方文档也提醒截图可能受环境影响。[视觉比较][playwright-visual]

自动可访问性检查可以发现一部分问题，但不能证明所有路径都可用。Playwright 的相关文档建议结合自动检查、人工评估和用户测试。[可访问性测试][playwright-a11y]

我们至少要实际走一遍：不用鼠标能否找到并完成主要操作？放大后是否还能读？错误是否只有颜色没有文字？对话框关闭后焦点到哪里？持续动画能否被控制？

### 本专题的最小验收清单

以下为待执行清单，不是本稿的测试结果。具体视口应根据目标用户确定；320、768、1280px 可以作为讨论起点，不代表覆盖所有设备。

| 场景                   | 要确认什么                                     |
| ---------------------- | ---------------------------------------------- |
| 没有点击任何演示       | 正文和来源可以阅读，没有自动执行外部任务       |
| 查看组件               | 演示启动、操作与预期一致，没有吞掉无关阅读交互 |
| 长中文标题和长网址     | 不遮挡主要操作，必要内容有可访问的展开或换行   |
| 只使用键盘             | 主要路径能完成，焦点可见，不被无关区域困住     |
| 减少动态效果           | 关键信息仍然存在，非必要运动按约定减少         |
| 资源来源不可达         | 可以继续阅读，失效项被标记，不编造取用说明     |
| 复制任务包失败         | 保留完整可选取文字，不显示虚假的复制成功       |
| 打开多项演示后继续阅读 | 页面不因无界工作明显退化；有问题能定位         |
| 与已有助手同时使用     | 文章、组件和助手的焦点与滚动不发生错误串扰     |
| 发布前                 | 内容、依赖、资产、来源和实际项目检查全部核对   |

### 验证标签必须说清楚范围

“官方说支持”“读过源码”“在我们的环境跑过”和“已经通过真机验证”是不同事实。不要让一个绿色 Verified 同时代表它们。

### 我们怎样验证这套方法本身

记录完成质量、选型错误、返工、人工纠正、时间与上下文消耗。不要只展示最好的一次结果，也不要把 token 更少直接当成更好。

**本章带走：** 有范围的验收结果。做过什么、没做什么、哪里失败，都应当能够被后来者理解。

## 08 把这套方法用到你的项目

**真正值得复制的，不是一句“你是顶级设计师”，而是目标、材料、约束、执行顺序和验收条件。**

### 先把前面几章的产出放在一起

| 材料           | 来自哪里 | 缺失时怎么办                       |
| -------------- | -------- | ---------------------------------- |
| UI Brief       | 第二章   | 先明确用户、主要任务与范围         |
| 参考和设计规则 | 第三章   | 不让 Agent凭形容词猜整套风格       |

### 配方一：先读取项目，再给出方案


### 三条可以直接采用的实践路线

| 你的目标             | 先做什么                                       | 第一轮合理产出                   |
| -------------------- | ---------------------------------------------- | -------------------------------- |
| 改造已有内容网站     | 读取现状，明确阅读与取用任务，先复用已有组件   | 一个局部可用区块，而不是推倒整站 |
| 给已有界面增加微交互 | 写清触发与状态，选择一个具体实现               | 一个行为准确、能降级的交互       |

### 一键的含义必须清楚

**复制材料** 只是生成文本； **发送为 Agent 草稿** 只是准备任务； **安装或执行** 会修改项目或产生外部操作。这三件事要分别表达。

当前本稿提供的是可复制的材料，不是自动执行能力。未来增加取用按钮，也应保留来源、范围、可能的费用与用户确认，而不是把所有动作藏在“Vibe it”后面。

**本章带走：** 一份适合自己项目的任务包。你可以从明确的一小步开始，不需要先装完资源地图上的所有工具。

## 持续共建：让每一次实践成为下一次的起点

**这个 Topic 不以发布为结束。值得长期保存的，是方法与可追溯的实践关系。**

### 这个页面自己的实践记录

我们采用一条朴素的产品原则：用我们讲述的方法建设 Vibes，并公开实际结果。它也适用于以后制作宣传视频、广告或其他 AI 作品：先形成方法，实际用于我们的需求，再把输入、修改、结果与限制写回专题。

但“采用过”“完成过”“效果更好”是三种不同结论。发布一支视频只能证明完成了制作；要判断传播或转化结果，需要另外的数据。UI 也是如此。

| 对象                 | 本稿中的事实                                   | 后续要补什么                     |
| -------------------- | ---------------------------------------------- | -------------------------------- |
| 原 beUI 页面         | 已有十种真实组件的源码导入、操作说明和来源     | 在新版叙事中的完整渲染与交互回归 |
| 当前 Topic 初稿      | 把演示重新组织到理解、选择、描述与验证的主线中 | 人工编辑、实际内容测试与发布记录 |
| 交互语义层           | 已给出格式与使用方法示例                       | 正式 schema、条目数据与验证工具  |
| 资源选择工作台       | 已明确任务与设计路径                           | 实际实现、操作验证与使用反馈     |
| 查看做法与任务包生成 | 已明确公开材料和权限边界                       | 交互实现、数据接线与相应验收     |

这张表会随着真实进展更新，但不会为了让页面显得完整，提前把设计目标改成完成事实。

### 什么样的贡献最有价值

你不必重写整个专题。补充一个准确来源、一条失效命令、一个不同环境的跑通结果，或者一个可以复现的失败，都能减少后来者的成本。

| 贡献类型     | 请提供什么                                       |
| ------------ | ------------------------------------------------ |
| 推荐一个资源 | 用途、官方来源、适用条件，以及为什么现有候选不够 |
| 修正一条说明 | 原描述、实际差异、来源或操作证据                 |
| 提交一个实现 | 固定源码、依赖、使用条件、接口与限制             |
| 提交跑通记录 | 项目和运行环境、版本、操作步骤、实际结果         |
| 提交失败案例 | 最小复现、预期与实际、影响范围；不要包含秘密     |
| 提供替代方案 | 同一任务下的收益、代价和可比条件                 |

可以通过 [Vibes 仓库][vibes-repo] 的实际协作入口提出修改。社区提交不直接等于默认版本的结论，涉及可执行代码、依赖和生产行为的修改需要额外审查。

### 更新什么，就记录什么

方法修订、资源版本变化和验证补充分别记录。修正一个链接，不代表整篇内容重新验收；某个环境跑通，也不代表所有浏览器通过。检索时，未知状态不能被当作支持状态。

| 记录日期   | 更新内容                                                             | 范围与限制                                                       |
| ---------- | -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 2026-09-12 | 形成 Topic 初稿；读取现有 beUI 页面与 MDX 规则；阅读主要资源官方说明 | 不包含新工作台的实现和整站验收；Bento Grids 正文与取用条件待复核 |

### 给资源一个位置，也给证据一个位置

长期维护可以把正文、资源、配方与验证记录分开存储，再由页面组合。MDX 负责叙事和组件编排，结构化记录负责检索、版本与机器读取；没有必要把几百条数据永远埋在一大块 JSX 里。

人看到可操作演示，Agent读取行为与接口，它们应该对应同一份来源记录。内容贡献与生产代码贡献分开处理，不让“人人可以完善知识”变成“人人可以未经审查执行代码”。

**Text 是 Block 之一，Demo 也只是知识的一种呈现。真正值得复用的是它背后的关系：解决什么问题、怎样工作、如何实现、在哪里有效。**

当你下一次看到一个喜欢的 UI，不必停在“收藏一下”。你应该能继续回答：它适合我的任务吗？我要取用哪个实现？怎样向 Agent讲清楚？最后怎样证明做对了？

这就是本专题希望建立的共同工作方式。
