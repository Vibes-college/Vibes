# Paseo原生助手接入计划

本计划是技术候选笔记，先完成[spec讨论状态](spec.md#讨论状态先厘清目的再选择方案)中的用户场景澄清，再重写为选定方案。默认Chat预设、正常对话执行与原生产出查看已确认；具体架构和完整计划尚未批准实施。

## 先向用户解释的取舍

| 候选                          | 用户能得到什么                                                  | 代价与限制                                                              | 何时值得选                                         |
| ----------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| 官方Web独立文档，加薄宿主外壳 | 原生连接/会话协调，减少路由和样式相互影响，可尝试保留旧顶部体验 | 仍有引导、桥接、活动与UI适配；iframe不隔离CPU，软键盘/历史/收起必须验证 | 核心需求能由普通官方App/CLI满足，且接入探针通过    |
| 官方Web直接挂入页面           | 更容易与主站视觉融合、共享页面交互                              | 已有实验需要多处路由/样式依赖补丁，升级维护更重；稳定性不因同页而提高   | 独立文档实测不能满足必要体验，收益足以抵偿补丁维护 |

这是源码支持的定性比较，不是实测性能排名或费用报价。两种接入均需要用户电脑与Agent环境；模型/Agent费用取决于所用provider，不由UI路线消除。托管资源、上游升级与排障的人力成本需在功能范围明确后估算。用户已明确Chat是默认配置，Build按需进入已有项目，standalone是独立模块接入便于维护；不需旧隐藏工作区后端或额外独立使用页面。compact/full的操作方式仍待讨论。

## 技术决定与职责

### 1. 可维护的原生应用边界

候选固定Paseo v0.7.2 / 9400a49，保留官方Metro/Expo导出和完整providers、HostRuntime、SessionProvider、timeline及原生操作。先验证独立文档容器，不继承PR #11深层依赖补丁与拆包探针。旧UI只作视觉、顶部操作、compact/full和状态保持参考；原因及源码见[research](research.md)。

拟新增文件在实现时按职责落地，不提前建立空模块：

| 位置                                            | 职责及边界                                                                         |
| ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| third_party/paseo-webui/upstream.json、patches/ | 源/锁/许可/补丁固定；每个补丁说明动机、影响、验证与升级移除条件                    |
| scripts/paseo-webui-build.ts、scripts/build.ts  | 重放官方构建并核实内容摘要；失败不复用过期产物，不手改生成JS                       |
| src/components/PaseoAssistant.astro             | 轻量按钮、安装引导和持久容器；随现有布局使用，不改变Explore导航                    |
| src/features/paseo/host.ts、contract.ts         | 单一iframe所有权、加载/重试/展示状态、焦点和受限消息；不创建SDK连接                |
| 内部Paseo文档与版本化 /vendor/paseo/ 资源       | 独立模块产物与宿主隔开维护；若采用文档容器，仅为嵌入载体，不另做独立使用页面       |
| 上游浅层UI/活动补丁                             | 极简顶部、普通视图入口、原生草稿附带、宿主活动入口；不自建状态投影、账本或恢复算法 |
| tests/paseo.spec.ts、tests/fixtures/paseo/      | 同一Playwright链路，先外壳回归，再真实协议/原生运行与分阶段负载                    |

接入验证必须证明Astro切页不重建iframe、原生history不污染宿主、布局/弹层/软键盘正确；若失败，保留证据并重新评估最小接入成本，不平行维护两种产品实现。

### 2. 用户路径与状态

宿主只持有未启动、准备中、原生就绪、加载失败，以及open/compact/full、当前公开作品。原生连接状态不等于宿主资源就绪；可聊天必须由原生明确状态决定。官方配对UI负责输入与保存秘密，宿主不二次解析或持久化。

首次点击先渲染引导，再启动资源准备；引导可滚动和交互，已安装用户可立即进入连接。预加载先下载，初始化选择不妨碍当前交互的时机；到可操作的路径不设倒计时。原生未准备好时保存最新展示参数，ready之后只交付当前状态；超时与资源失败有有界重试，不重发用户操作。

桥接按版本、origin、source、消息类型和字段大小校验；只有ready/error、展示/语言/活动、公开资料草稿与关闭意图，不接受任意RPC、HTML或可执行代码。草稿进入原生composer后由原生管理；宿主不复制聊天历史。配对材料不放query、分析、日志或Git。

收起保持同一根与连接，向原生输入表面可见/焦点/页面前台三个真实信号。只暂停不必要显示工作；不断开全部同步来制造低CPU。真正退出、主动断开、忘记设备分别走官方能力并核对存储与迟到回调；不得把任意清缓存当作内存优化。

FR006已明确：Chat预设免目录浏览、免Agent/模型/强度选择，正常执行与产出能力保留。可在原生启动界面调用官方createProjectDirectory/addProject及复用工作区的现有能力，准备原生draft默认值；用户首次发送时沿原生Composer创建Agent，不在每次打开时创建空会话。Codex/Luna先按真实模型目录选择，强度优先使用该模型原生默认值。Build保留原生已有项目选择与配置路径，不被Chat默认值覆盖。

预设只保存按host划分的已确认默认目录/工作区选择，不复制历史或恢复器。目录使用daemon侧home解析，名称和存放位置是实现候选；已存在对象须核对目录类型，不清空/覆盖。目录/工作区创建不是全部幂等，断线后先通过官方查询确认结果；单窗口重复点击互斥，跨标签并发边界据实验证，不能承诺服务端没有提供的恰好一次。代价集中在这个有限的首次准备流程，不需新增daemon/protocol。

产出使用原生聊天文件链接→工作区文件面板→原生预览路径，保留它需要的内部工作区、读取订阅、编辑器基础库、富文本和图片支持。用户已明确不新造；不为PDF/Office或纯relay下载增加服务。固定版本不支持的能力记录限制；原本支持而被Vibes容器/CSP破坏的能力属于接入回归，仍须验证。

### 3. 生产策略和依赖

先检查已存在且正确归属的Paseo与开发服务，可复用才复用；必要新实例使用任务目录和空闲端口，不覆盖用户全局Paseo或Agent配置。复用旧安装前核对source/lock/patch状态，不在另一个任务的源码或node_modules应用补丁。

Vibes保持Astro/TypeScript；独立文档承载上游自己的React/Expo依赖，不把第二套React塞进主站。优先复用已经核验的构建资产与官方锁文件；新增安装前列明确切工作区、锁摘要、必要性和命令，按仓库规则取得同意，不以引入预构建包绕过来源和许可核查。当前阶段未新增依赖。

生产头只增加接入必要的明确来源；/paseo/可由本站嵌入，宿主保持自己的frame-ancestors策略。核实Cloudflare多条头部规则合并后的实际响应，不能凭配置文字认定生效。插件动态求值冲突先核对必要路径，不全站放开unsafe-eval。

## 宪章检查与预算

保留Explore全部现有硬预算，未启动助手不下载专用资源。助手完整清单计量原生与宿主增量、初次/按需请求、缓存命中及解析初始化，不能按目录一律排除未知脚本。新助手独立资源上限在完整未裁剪候选产物确定后据真实清单和托管限制制定，先记录再作为交付检查；不继承012的首包减半目标，也不把未知上限伪称已通过。

不改协议/同步算法，不新增本地服务产品、账号或站内编辑。Chat默认目录不限制Agent权限，沿用原生正常执行规则。Chat快捷预设、Build已有项目、原生产出查看和独立模块边界已确认；compact/full和安装配对仍待收敛。源码接入、兼容与测量是计划确认后才开展的工作，不用“官方”代替结果。

### 分阶段测量协议

同一设备/浏览器版本、视口、CPU设置、网络、daemon/provider版本及固定内容，对照未改官方Web；Explore用同SHA未启动助手的页面作对照。记录硬件、环境、构建SHA、源/补丁摘要、样本顺序和原始文件。每组20次交互；冷与暖各独立profile组，交替运行对照和候选，不跨组共享缓存污染结论。这些是工程对照，不能称真实用户现场INP或公网统计。

| 阶段      | 操作与结果                                                          | 辅助诊断                                                           |
| --------- | ------------------------------------------------------------------- | ------------------------------------------------------------------ |
| S0 未打开 | 搜索、滚动、详情切换，无助手资源与连接                              | 请求、主站交互与长帧基线                                           |
| S1 首开   | 未安装引导、已安装直接连接、已配对恢复；分别冷/暖、慢网、离线、失败 | 点击至可见、下载、解析初始化、连接、历史同步至可操作分别计时       |
| S2 使用   | 1000条历史、20秒流式、工具展开、100k字符长消息、输入及滚动          | 本地交互p95、INP可用值、>50ms长任务、>50ms长帧占比、数据到呈现延迟 |
| S3 收起   | 空闲、持续流式、待审批各自收起后操作Explore                         | 同S0操作差值、原生活动信号、必要消息、CPU和渲染工作                |
| S4 恢复   | 20轮开合/compact/full/切页，断网/刷新/后台前台，草稿和旧滚动位置    | 实例/socket/监听器、实际提交次数、资源重下与恢复到可操作时间       |
| S5 长时   | 固定总历史量重复负载60分钟，30轮开合，周期回到相同静置状态          | CPU、内存峰值与静置平台、可回收资源、结尾重复S2/S3                 |

长时测试将固定内容循环与真实历史增长分开；每轮静置60秒后采样，报告自然GC造成的波动，不把单点堆值或强制GC后的下降当作泄漏证明。检查DOM、监听器和连接是否无界增长；内存持续单调趋势与CPU不回落须定位。官方同负载也不通过绝对交互门槛时如实记录上游限制，先讨论取舍，不扩大门槛或悄悄重写核心。

长帧用相同浏览器支持的计时方式计算，缺少指标记不可用，不记零；浏览器trace/CDP/系统CPU仅作诊断，不维护第二套E2E。首次回答拆开模型/工具等待、网络到达和呈现延迟。滚动恢复允许2px布局取整误差，底部跟随状态单独断言。

恢复矩阵最少覆盖4个操作状态×3种中断，各3次；更换网络、长时间锁屏及iOS实际挂起需真机单列。自动化可靠操纵的网络/页面生命周期与真机结果不混算。重复提交用daemon操作记录验证，不能只观察卡片数量。

## 验证与交付

本批只有规格Markdown与索引，运行docs:check和format:check。产品、构建或测试改动按项目full执行verify与budget；不改变检查分类或降低必需门槛。

真实官方配对/中继、模型、工具、审批、停止边界、断线、刷新、导航与长期使用通过后才认定接入可交付；同SHA预览核对实际响应头和资源路径。iPhone真机缺席时保留明确待测，不能用模拟结果勾选真机。

代码同步docs/features/local-assistant.md、浏览/阅读入口、docs/system/local-assistant.md及configuration/interfaces/rules/checks-and-release对应段落与code-sources，再复核文字后更新摘要；索引和PROJECT_ANALYSIS随最终行为变更。全部任务实做后spec/plan/tasks与索引改complete。

## PR工作台与经验复核

按[tasks.md](tasks.md)在同一Draft PR推进：规格与待决策→最小完整接入→真实正确性→六阶段测量→有证据的修正→交付。先体验再决定优化点；未发现退化可不做性能补丁。

现有LESSONS中的异步导航、真机证据和WebKit媒体回归继续适用；PR #11曾记录原有音频测试间歇失败，新最终验证若复现要定位或报告，不能删测试掩盖。Ready前由独立工作区的另一Agent审查整个PR和最终SHA，涵盖正确性、秘密/权限、后台资源、上游补丁维护、测试与生产交付。用户决定合并，之后逐commit及最终差异复核docs，同步main、验收部署并只清理本任务资源。
